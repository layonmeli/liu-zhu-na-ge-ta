# 把意思写成本人的话

以下方法由本技能重新组织；sources.md 中 NVC、感恩、道歉、温和开场等资料及部分开源流程提供启发，采用范围见 [GitHub对照](github-integration.md)。结构服务表达，不是成功沟通公式。

## 真诚：让说法、用意与行动对得上

先理解用户确实想说什么，再润色。真诚可以直白，也可以含蓄、笨拙或尚未完整；不以文案感人程度、披露多少隐私、对方是否满意来评判。

- **不为效果补情绪。** 用户没有说过，就不写“我哭了一夜”“你是我最重要的人”“我已经彻底想明白了”。用户让文案更真诚时，优先找具体事实、删掉空话或保留真实的不确定；不能靠增加未提供的情节与感情完成。
- **请求按请求说。** 用户实际想请对方帮忙、联系或改变做法时，帮助把这层意愿说清，不包装成“我没有任何要求”，也不把拒绝写成考验对方。若用户只是感谢，就不附加请求。
- **承诺按本人愿意承担的范围说。** 分清已做的改变、正在尝试的改变、尚未决定的建议；没有做过不写成已经做到。尚不能作出长期承诺时，可以直接说目前能做什么或还需要想清楚什么。
- **保留复杂与限度。** 感激、委屈、想靠近和想保护自己可以并存。用户选择不讲某些细节时，表达“这部分暂时不想谈”即可，不要求完全披露，也不编一个更好听的理由。

如果感谢、歉意或抒情换个对象也能原样发送，可静默检查是否遗漏了用户已经提供的具体处境；有合适细节就换进去，材料少就保留朴素短句，不凑细节或追问隐私。简短通用的“谢谢”“对不起”本身不因此失去真诚。

辅助者同样诚实：说明理解来自哪些已提供的内容，拿不准时允许用户修正；不要声称完全懂其内心，不用假装自己也经历过类似事件来制造亲近感。不直接给用户贴“真诚／不真诚”的人格标签。

## 先选这一次的目的

| 目的 | 建议保留的内容 | 避免 |
| --- | --- | --- |
| 感谢 | 对方做过什么、自己记住什么、对自己有什么具体意义 | 只写伟大、温暖等空泛赞美；把感谢变成欠债 |
| 分享喜悦/为对方高兴 | 具体的好事、此刻的高兴、为什么想让这个人知道 | 自动挖背后的伤痛；把分享写成索取赞美或贬低他人 |
| 想念 | 让自己想起对方的小事、想分享的近况、可选的邀请 | 用“你都不找我”测试在乎程度 |
| 解释行动里的关心 | 自己确实做过的事、经用户确认的用意 | “我都做了这么多，你该懂我” |
| 表达委屈 | 可定位的事件、实际影响、期待或边界 | 为求好听删除不舒服；将所有责任退回用户 |
| 道歉 | 自己的行为、已知或谨慎描述的影响、承担责任、可行的补救 | “如果你觉得受伤”；“但是你也”；保证对方必须原谅 |
| 修复/重新联系 | 想重新交流的意愿、本人愿做的具体改变、对方选择空间 | 保证复合；把暂时沉默当同意；借第三人施压 |
| 设立边界 | 哪件事不能接受、自己可控制的下一步 | 威胁惩罚；把边界写成操控他人的规定 |
| 告别/纪念 | 想保留的回忆、未说完的话、当下真实状态 | 逼迫释怀、强求感恩或原谅 |

混合目的可以共存，但一条消息通常围绕一个主旨；例如道歉里不要暗夹索取安慰。用户选择表达多个重点时，帮助组织而不是擅自删掉。

### 被听懂，还是希望有个行动

先参考用户已经说出的目的；确有歧义时才问“你更想让他知道你的心情，还是希望他具体做点什么？”不要自动替用户选。

- 如果只是想被听懂，表达完整就可以结束，不自动增加“多陪我”“每晚给我打电话”。
- 如果想提出请求，把“你要在乎我”逐渐落到用户认可的一件可回应的事；做法由用户选择，不由模型代为承诺或规定。
- 如果既想被听懂又需要解决事，可以先讲核心意思，再带一个小请求。不把请求写成爱的证明，不用拒绝该请求判断对方是否在乎。

用户想获得支持时，可把已明确的支持方式直接写出来，例如“我想说说今天的事，先听我讲就好，暂时不用帮我想办法”。这是可选的具体请求，不意味着对方必须随时有空，也不要求每次倾诉先解释支持类型。

### 已经说清，以及只愿说到这里

已经清楚表达过而对方没有理解、回应或照做，不自动判断是措辞不够好。区分“尚未说清”与“已经说清但没有得到想要的结果”；按用户这次的目的，支持重申、选择自己可控制的下一步，或停止这轮沟通。表达清楚不等于对方一定同意；也不单凭没照做推断故意伤害。

道歉只承担用户确认属于自己的具体行为及影响，不把合理的感受、拒绝或诉求一并撤回。承担责任与保留边界可以分别说清，不用“但是你也”抵消道歉，也不必写成“全是我的错”。联系合适、意图明确时可以直接说明这件事，不强制先发“在吗”“还生气吗”，让对方先报告情绪或安抚自己才开始道歉。

同一问题反复发生时，先看用户是否已经说明先前的承诺和这次愿意改变的具体做法。若有，承认承诺与行为的落差，写清这次确实可执行的一点；若没有，不替用户编补救计划，也不把再次道歉升级成更强烈的保证。必要背景可以说明，但不取消本人行为责任。对方是否接受，要等其真实回应，不能要求因道歉而立即恢复信任。

真实表达允许只说一部分、暂不解释原因。用户已经决定不说细节时，帮助保留这个范围，不追问秘密、不编理由、不擅自承诺以后会讲。面向第三人或公开发布的表达，还需按 [隐私边界](boundaries.md) 检查受托的私事。

## 写作顺序

1. 从用户的话里提取两三个有辨识度的词，保留称呼和说话习惯。
2. 选最有分量的一件真事。不要堆时间线来证明谁付出更多。
3. 把确认过的意思放进去。感受不明确时可以保留“我说不好”。
4. 只有需要时加入请求、边界或行动承诺；承诺必须来自用户或清楚标为供选择的建议。
5. 朗读式检查：像微信还是演讲？本人真的会说这句话吗？去掉为了催泪而添加的金句。

不是每条话都要“我感到……因为我的需要是……”。例如“你送来的那顿饭，我到现在还记得。那天我真是觉得有人在惦记我”，可以比完整公式更自然。例子只示范结构，不能把其中的事塞进真实用户经历。

### 用已有聊天校对本人语气

从用户主动提供的记录里，优先看同一对象、相近场景下的两三句平常表达：常用称呼、句子长短、是否使用表情和语气词、表达有多直接。这只是当前草稿的语言参考，不是人格画像。材料不足就沿用当前说法，不要求导出更多私聊。

不要把气头上的攻击、刻意敷衍或强忍的客气当作其唯一风格，也不照搬骂人和施压部分。用户希望尝试更直接的说法时支持这种变化。不要为了“像真人”故意加错别字、断句、撒娇、自嘲或表演性的停顿。

## 关系适配

- **朋友**：维持友谊语气，不擅自加入恋爱告白、占有或排他要求。久不联系时可以轻一点，也允许明确说“我很珍惜你”。
- **恋人/伴侣**：可以坦白想靠近、孤单或受伤，但不把“爱”当取消边界的理由。称呼和亲密程度以用户为准。
- **父母/长辈/亲人**：可以从吃饭、回家、照料等具体生活切入。不给“家人当然都爱你”这种结论，也不把孝顺、辈分设成表达义务。
- **孩子/晚辈**：措辞符合年龄和理解能力。成人为自己的行为负责，不让孩子负责成人的孤独、婚姻或情绪稳定。
- **其他重要的人**：尊重师生、同事、照护等情境的实际边界，不自动套爱情叙事。

含蓄和直白都可用，不按性别、民族或年龄推定偏好。先参考用户原话；不够时才问“更像平时聊天，还是认真写一封信？”

**对方可能接不住。** 很多家庭里，第一次听到这类话的人会岔开、开玩笑，或回一句“整这些干啥”“没钱了？”。这常常是不好意思，不等于没听见；但不要据此断定具体某个人的心意。用户担心这一点时，可以给一句接话（如“没啥，就是想说一声”），或建议不需要当场回应的载体。用户只要文案时不加。

**浓度由用户选。** 第一次说“我爱你”“谢谢”这类话、又没说明想说到多直白时，可以在主稿外附一句更轻的说法（一件具体小事、一句惦记或一个小请求），由用户决定说到哪一档；只附一句，不展开成多个版本。

## 表达载体

| 载体 | 写法 |
| --- | --- |
| 一句话 | 一件事或一个意思就够，适合第一次开口 |
| 微信/短信 | 短段落、一个主旨；长短随用户习惯，不机械加“你不用回” |
| 语音稿 | 短句、有自然停顿，不写舞台表演指令 |
| 当面说 | 给一个开场和最核心的一句；可先询问现在是否方便聊 |
| 一封信 | 场景、意义、想说的话；不按篇幅扩写虚构回忆 |
| 照片/旧物旁注 | 用户选定的画面或物件配一句自己的解释，不替图片下心理结论 |
| 小行动加短句 | 使用双方接受且适度的动作，把真实意图讲明白，不用昂贵礼物替代责任 |
| 不寄出的信 | 写给自己保存或当场读完即可；是否保存、展示或分享由用户决定 |

可以纯粹用非语言表达，不把能否说“我爱你”当作完成指标。拥抱、握手、送礼、到访都要考虑对方意愿和情境；不得拿这些方式绕开拒联。

## 修改示例

- 抽象：“谢谢你一直以来的付出。” → 如果用户确实提供这件事：“那天你陪我等到末班车，我一直记得。”
- 债务：“我对你这么好，你怎么还走？” → 若用户确认这份意思：“我很舍不得，也希望有机会把我的想法说清楚。”不承诺因此可以联系已拒联的人。
- 伪感受：“我觉得你很自私。” → 依据确切事件：“昨天我还没说完，你就结束了通话，我很失落。我希望下次能有时间把话说完。”
- 抹平：“算了，都是为我好。” → 若用户本意如此：“我知道你可能在担心，但当众说那些话让我难堪。我希望以后这类事私下谈。”不知道对方用意时删去第一句。
- 空承诺：“我以后一定都改。” → 先问用户具体愿做什么，再写可履行的一件事；未经用户提供，不编“每周陪你”“永不再犯”。

## 交付与后续

默认给一个能用的版本，必要时附一句核心理解；不要求用户阅读完整心理分析。用户要深入分析时，展示“你说过的内容”和“可能的理解”，允许修正。

可以用几个可能回应练习表达，但必须说清这是练习、不是对方的预测。对方沉默时不推断为冷漠或暗示继续追问；对方拒绝时承认其选择。不要自动生成连续催促计划。

### 开口以后，接住实际发生的回应

用户带回新回复时，围绕这一条继续，不重新写整篇或执行预设的追发时间表。对方指出具体影响时，先处理已知影响；提出问题时回答该问题；明确拒绝或要求空间时，尊重该范围。只有用户主动要演练时才给少量假设分支，不把脚本中的反应当作真实对象的态度。

### 用户试说后的最小修改

用户带回自己写的版本、说“别替我写，帮我看看”，或主动想练习时：

1. 先指出一句已经准确表达了本人意思的话，不重新包办整篇。
2. 若有明显偏差，只挑最影响核心意思的一处，比较“本人确认的意图”和“这个措辞可能被听成的意思”。后者是文字可能造成的歧义，不是对真实对象的预测。
3. 提一个保留本人语气的最小改法，或让用户自己换那一句。不要突然添加道歉、解释、亲密称呼或未来承诺。
4. 用户确认“这样就是我想说的”就停，不反复打分或追求完美措辞。

### 用户想复盘时，分开表达与结果

先取用户实际说过的一小句，说明它已经表达了什么、哪里仍有具体歧义；再区分对方实际回应和仍然未知的部分。可以指出一处值得保留的表达和一处最小修改，不用分数、人格结论或长篇教练报告。

评价当时的措辞，要依据当时已经知道的信息；不能拿后来才披露的情况责怪用户当初没猜到。复盘中分开“某人提出了什么”“另一方明确同意了什么”“后来实际完成了什么”，保留各自的范围。答应一个安排不证明已经原谅、没有受伤或恢复信任；尚未回复的最后一句也不自动证明用户故意回避。

对方答应，不足以证明这套措辞适合以后所有场景；对方拒绝，也不自动证明用户表达失败。例如用户已经清楚、无威胁地提出一个请求，可以肯定请求说得具体，同时承认对方有现实限制或自己的选择；具体原因未知就留白。存在真实攻击或含糊之处时仍如实指出，不能为了鼓励而空泛说“你已经做得完美”。

只有用户希望继续修改或练习时，才支持再试一句。复盘的出口也可以是“已经说清，先停在这里”。

### 文字越写越长时

用户希望继续沟通，而当前消息不断变长、同一处误解反复出现时，可先帮其写出眼下最重要的一小句，再由用户决定其余内容是否另找时间展开。是否换成语音、电话或当面，由双方意愿、表达习惯和安全情况决定；不设置固定冷静时长，不默认见面更好，也不把暂停当成惩罚或吊胃口的策略。

以上新增做法参考开源Skill后重新组织；具体出处及未采用部分见 [GitHub对照](github-integration.md)。

### 担心被看出是 AI 写的

如实说明哪些是用户自己的事和话、哪些是连接句。建议按自己平时发消息的习惯重打一遍，或手写、当面读出来。告不告诉对方由用户决定，可以给一句诚实的说法；不教隐瞒技巧。
